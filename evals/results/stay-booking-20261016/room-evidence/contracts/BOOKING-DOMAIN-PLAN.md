## Product decisions to freeze before the next request

- Detail: real return route with a direct-entry fallback; property photo and identity, trip dates/guests, then two actual rooms with eligible rates. Each room owns its capacity, bed description and inclusions. Each rate owns its price and cancellation condition; its selection action is below the facts. No fabricated reviews, inventory urgency, hosts, amenities or desktop layout.
- Eligibility: dates, guests, closures and selected filters continue to apply. A cheaper ineligible rate cannot replace the selected rate. Changing trip inputs invalidates/recalculates a selection before review rather than silently retaining an old quote.
- Review: small subordinate property/room/rate summary, editable trip details, itemized nightly×nights, one cleaning fee, integer service fee and total. Then the minimum guest fields. A valid local request is the completion condition; do not imply that a supplier received or confirmed it, that money was charged or that a refund occurred.
- Request persistence: reads must validate the complete schema before any write. Missing storage alone means confirmed empty. Malformed, unknown-version, invalid-ID or provider errors remain unknown, preserve raw bytes, disable mutation and provide explicit recovery. Ordinary write errors preserve draft and existing data and allow ordinary retry.
- Create/edit identities: create receives one stable operation ID before the first attempt; repeat submission of that same ID/content returns the existing result. A conflicting payload with the same ID is an error. Editing preserves identity and createdAt; increments revision and updatedAt only after persistence succeeds. Starting a fresh request clears edit identity.
- Management: list → request detail → change trip/room/rate → review price delta → explicit save; cancellation → review selected request and condition → explicit confirmation → cancelled request. Status and primary outcome outrank subordinate property facts. Cancelled data remains readable; there is no automatic destructive delete, archive or fake refund.
- Recovery: failed create/change/cancel leaves original records and in-memory committed state unchanged. A read-failure attempt cannot overwrite restored data. Reload explicitly validates restored records before enabling mutation. No sensitive guest draft is automatically written as an autosave.

## Planned bounded units and acceptance

1. Rate/quote adapter: strict IDs and trip schema, preserve all selected IDs, use accepted offer selection against one room/rate, return an immutable complete price snapshot. Verify exact totals, closure bounds, capacity, invalid dates/IDs and nonmutation.
2. Strict request-record validation and store: versioned schema, explicit injected storage/clock/ID; no browser DOM. Verify initial-read faults, duplicate/conflicting operation IDs, atomic create/change/cancel, stale revisions and write retries. These tests do not establish visual quality.
3. Room selection and review: stable semantic markup and bounded controller/render units. Verify actual connected browser actions and back/re-entry, draft preservation, selection invalidation and total/cancellation hierarchy.
4. Local calendar/guest controls: actual range and capacity constraints, keyboard and touch targets, cancel/confirm semantics, month changes and return focus. Native input behavior remains unverified until replaced/tested or explicitly scoped.
5. Request management UI: real persisted list/detail/change/cancel states and fault recovery. Then complete HTML/CSS, typography, official icons, all widths/enlargement, active catalog/eight-guide evidence and repeated direct source-bound reference comparisons.
